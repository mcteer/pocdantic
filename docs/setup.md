# Reusable PoC setup

Use this route for a colleague's sign-in and a read from a Vault-backed PostgreSQL database.
No source edits are required. Each deployment needs its own provider and Vault configuration.
Optional phone, delegated exchange, remediation, governance and audit demonstrations have
separate requirements; ordinary sign-in does not establish their support.

## Start here

You need Python 3.12+, [uv](https://docs.astral.sh/uv/), a checkout of this repository,
and access to an OIDC provider, Vault and PostgreSQL. Run all commands from the checkout
root. An offline preview needs none of those services:

```sh
uv sync --locked --group dev
uv run agent demo
```

For a live PoC, first obtain the administrator settings below, then follow
[Start a fresh workspace](#start-a-fresh-workspace). Use a separate checkout and private
configuration for each deployment. If you already have enrolled state, start with
[Existing installations and recovery](#existing-installations-and-recovery).

To have a coding agent help, open the checkout in your harness and use this prompt:

> Read AGENTS.md and docs/setup.md. Help me configure and start the portable browser
> PoC using my OIDC provider, Vault and PostgreSQL. Perform the local setup and readiness
> checks, preserve existing configuration and recovery state, and give me exact steps
> for missing administrator settings or human sign-in. Keep secrets out of chat and logs.

## Configuration worksheet

Enter these settings in the private `.env.local` generated by `agent setup init`.
URLs, audiences and roles come from your deployment's administrators; example values
are not working credentials. The following table covers the Google-backed browser baseline.

| Settings | What to enter / who supplies it |
| --- | --- |
| `DATABASE_AUTH_MODE` | `user-jwt` for this guide. |
| `OAUTH_PROVIDER` | `generic`; works with an explicitly configured issuer/discovery. |
| `OAUTH_DISCOVERY_URL`, `OAUTH_ISSUER` | Exact discovery document URL and issuer from the identity administrator. |
| `OAUTH_AUDIENCE` | Database API audience present in the signed user access token; distinct from the login client ID. |
| `OAUTH_ACCESS_TOKEN_TYP` | Actual access-token header type: default `at+jwt`, or `JWT` if that is what the provider issues. |
| `LOGIN_CLIENT_ID`, `LOGIN_CLIENT_SECRET` | Confidential browser application's ID and secret from the identity administrator. |
| `LOGIN_SCOPES` | `"openid database:read"`; the application/user must be granted that database scope. |
| `VAULT_ADDR`, `VAULT_NAMESPACE` | HTTPS Vault address and namespace if applicable, from the Vault administrator. |
| `VAULT_JWT_AUTH_MOUNT`, `VAULT_JWT_AUTH_ROLE` | Existing JWT mount and constrained human role configured below. |
| `VAULT_DATABASE_MOUNT`, `VAULT_DATABASE_ROLE` | Dedicated database secrets mount and SELECT-only credentials role. |
| `DATABASE_HOST`, `DATABASE_NAME`, `DATABASE_PORT` | PostgreSQL host, database and port (default `5432`), from the database administrator. The database needs `poc_records(id, status)` and a test record with ID 1. |
| `GOOGLE_API_KEY` | Your model API key, entered privately. `MODEL` has a default; other model integrations are described in the configuration reference. |
| `OAUTH_CA_FILE`, `VAULT_CA_FILE`, `DATABASE_SSLROOTCERT` | Local CA bundle paths where private trust is required; each service has independent trust settings. |
| `OAUTH_TRUSTED_HOSTS` | Leave `[]` unless OIDC advertises endpoints on additional hosts; enter their exact DNS names as a JSON array. |

The browser obtains its user token through sign-in. No database password, administrator
token, saved `BEARER_TOKEN` or separate agent OAuth client is needed for this route.

## What to request from your administrators

Ask the identity administrator for an HTTPS OIDC issuer/discovery URL, a confidential browser
application, its client ID/secret, and the exact callback
`http://127.0.0.1:8000/auth/callback`. Request authorization-code login with PKCE S256,
RS256-signed access JWTs carrying a database audience distinct from the login client ID
and `database:read` scope,
and signed ID tokens. Supply the actual access-token header type through
`OAUTH_ACCESS_TOKEN_TYP` (default `at+jwt`; use `JWT` when the provider issues that type).
Access tokens must outlast `TIMEOUT_SECONDS` plus the 30-second cleanup reserve.
Request refresh tokens only if you add `offline_access` to `LOGIN_SCOPES`.

For Keycloak, register an OpenID Connect client with client authentication and Standard flow,
the exact redirect URI, the needed audience mapper and scope mapping. Obtain discovery from
`https://identity.example/realms/poc/.well-known/openid-configuration` with issuer
`https://identity.example/realms/poc`. Check the returned token claims rather than assuming
that the client ID is the database audience. See [Keycloak OIDC endpoints](https://www.keycloak.org/securing-apps/oidc-layers).
For IBM Verify, ask the tenant administrator for the confidential OIDC application's discovery,
issuer, audience and assigned scopes; use the tenant's configured identity source for login.
The runtime does not require a Verify administrative API client for this baseline.

Ask the Vault administrator for the HTTPS address, optional namespace, JWT auth mount/role,
and a dedicated database mount/credentials role. The database administrator must restrict
that role to SELECT on the table used by the existing fixed query; see
[database preparation](usage.md#vault-and-database-boundary). Share private CA bundles if required.

The following administrator examples use synthetic selectors. Replace their values in private
files and submit them using an authenticated Vault CLI session. Do not add an administrator
token to the browser baseline or paste it into commands. Existing mounts must be inspected
before use; these examples do not create a database connection or change PostgreSQL grants.

Dedicated `poc-read.hcl` policy:

```hcl
path "team-db/creds/reader" { capabilities = ["read"] }
path "auth/token/lookup-self" { capabilities = ["read"] }
path "auth/token/revoke-self" { capabilities = ["update"] }
path "sys/leases/revoke" {
  capabilities = ["update"]
  required_parameters = ["lease_id", "sync"]
  allowed_parameters = {
    "lease_id" = ["team-db/creds/reader/*"]
    "sync" = [true]
  }
}
```

Private JWT mount configuration `jwt-config.json`:

```json
{"oidc_discovery_url":"https://identity.example/realms/poc",
 "bound_issuer":"https://identity.example/realms/poc",
 "jwt_supported_algs":["RS256"]}
```

Private role definition `human-role.json`:

```json
{"role_type":"jwt","user_claim":"sub","bound_audiences":["records"],
 "bound_subject":"synthetic-authorized-user",
 "bound_claims":{"scope":["database:read","openid database:read"]},
 "token_policies":["poc-read"],"token_no_default_policy":true,
 "token_type":"service","token_ttl":"240s","token_max_ttl":"240s",
 "token_explicit_max_ttl":"240s","token_period":0}
```

Match the actual scope claim format exactly; do not use an unbounded wildcard.
The administrator chooses the permitted subjects/groups and must inspect effective identity
policies too. With the JWT mount already enabled:

```sh
vault policy write poc-read poc-read.hcl
vault write auth/jwt/config @jwt-config.json
vault write auth/jwt/role/human @human-role.json
```

A service token may be renewable; this application never renews it. It checks lookup-self for
an explicit maximum of 1–300 seconds and enough remaining time for the operation plus cleanup.
The provider policy permits cleanup within the dedicated role. The adapter additionally limits
cleanup to its exact recorded lease. This baseline is role-scoped authority, not per-lease
RAR delegation. Consult the [JWT role API](https://developer.hashicorp.com/vault/api-docs/auth/jwt)
and [policy parameter constraints](https://developer.hashicorp.com/vault/docs/concepts/policies).

## Start a fresh workspace

```sh
uv sync --locked --extra server --extra postgres --extra google --group dev
uv run agent setup init --mode user-jwt
```

Edit the generated `.env.local` privately. Fill the issuer/discovery/audience, LOGIN client,
Vault address/role, database target/host/name and model key supplied above. Set
`LOGIN_SCOPES="openid database:read"`. A browser sign-in supplies the user token;
leave `BEARER_TOKEN`, agent `OAUTH_CLIENT_*`, `VAULT_AUDIENCE` and Verify admin credentials
unset. A repeated init preserves the existing file and recovery state.

Use `OAUTH_TRUSTED_HOSTS` only when advertised OIDC endpoints use other hosts: a JSON array
of at most 16 exact DNS names, without URLs or wildcards. Set `OAUTH_CA_FILE`,
`VAULT_CA_FILE` and `DATABASE_SSLROOTCERT` independently for private trust bundles.
HTTPS verification remains enabled. See [configuration](configuration.md) for aliases.

```sh
uv run agent setup check
uv run agent setup check --network
uv run agent recover init
uv run agent respond init --prepare
# Inspect .local/response/policy.json; leave automatic provider cleanup disabled.
uv run agent respond init
uv run agent workspace
```

The response commands enroll the existing local safety controls, without changing providers.
Run first-time enrollment only for absent state. The default check is local; `--network` reads public metadata/seal status and tests TCP
reachability without issuing credentials. Exit 2 means configuration/dependency repair,
3 means recovery repair. Follow the returned setting names and instructions. A healthy
provider is not proof of permission. Open the printed loopback URL, choose Sign in,
complete your provider login, choose `database-reader`, and request record 1.

After first-time enrollment, rerun `uv run agent setup check`. Missing local enrollment
can produce exit 3 on the first check even when provider configuration is correct.
Success means the workspace returns from login, the record read completes, and
`uv run agent recover status` shows no unresolved credential attempts. Stop the workspace
with Ctrl+C when finished; retain its private configuration and recovery history.

If setup fails, use the reported `missing_settings`, reason and next action. For exit 2,
repair the named settings or install the missing extras, then repeat the check. For exit 3,
inspect recovery/response status and follow the exact repair steps; do not delete `.local/`.
If an administrator is needed, give them the failing boundary and the matching request
from the section above. Share only sanitized errors, never tokens or raw provider responses.

## Fixed live validation

These commands are separate from setup. They issue a native Vault token and database lease,
perform the fixed read, then attempt exact synchronous lease cleanup (20 seconds) and token
self-revocation (10 seconds). Both cleanup outcomes must be confirmed. No administrator
fallback is attempted after denial or failure.

For command-line validation, place an appropriately scoped signed user access token in
`BEARER_TOKEN` privately and a second valid token **without** `database:read` in
`PORTABILITY_DENIED_TOKEN`. Do not put either token in command arguments.

```sh
uv run agent validate ready --suite live-portability
uv run agent validate run --suite live-portability --mode live --scenario user-jwt-read
uv run agent validate run --suite live-portability --mode live --scenario user-jwt-denial
uv run agent recover status
```

Read should pass with both credentials resolved. Denial should pass with zero Vault issuance
and zero SQL effects. Private run artifacts record route, source product, context and time.
Configuration, metadata, synthetic runs and stale/foreign evidence cannot promote capabilities.
Recent sealed native captures with matching source correlations can demonstrate the database
baseline. Original delegated/native acceptance criteria remain separate; the original closeout
command accepts its four original cases only.

Repeat independently on IBM Verify and Keycloak with different Vault instances. Record actual
versions and sanitized results in the feature validation record; store raw evidence under
ignored `.local/`. An unfamiliar colleague must perform two fresh setups; record elapsed time,
exclude only documented provider waits, and require no undocumented assistance or source edits.
Those live and colleague checks are not established by automated fixtures.

## Existing installations and recovery

Stop the workspace before migration. Resolve every outstanding attempt using the original
configuration before changing mode, namespace, trust or target. Then edit private configuration
and run `uv run agent recover migrate`; v3 preserves resolved legacy history. Repeat migration
is a no-op. Existing response/governance enrollments also pin their original context;
recovery migration does not rewrite those policies. If their status reports a context/policy
mismatch, restore the original configuration to inspect or resume that installation. Use a
fresh clone/working directory with its own private state for an independent deployment.
New portable reads require v3 enrollment. Never delete, reset or reinitialize an
existing journal to bypass unresolved state.

For a failure, run `uv run agent recover status` and use its exact incident ID with
`agent recover revoke --incident ID`. Known native tokens use captured
self-revocation authority; lease cleanup uses its captured parent when available. If exact
cleanup authority is unavailable, the operator needs narrowly scoped recovery authority and
matching reviewed Vault request/response evidence. Expiry, a later 403, or token cascade
alone does not establish an independent successful lease cleanup. Lost responses remain
blocked until exact native evidence resolves the uncertainty.

Keep `DATABASE_AUTH_MODE=delegated-exchange` for the existing advanced route; it remains the
compatibility default and requires the separate actor/client and delegated audiences.
Switching modes is explicit. Unsupported advanced features do not cause automatic downgrade.
